Design System

The single authority for how this application's UI is built: which tokens, classes and markup patterns to use. Every page follows it. When a page and this document disagree, the page is wrong.

Changing the system

  1. Use a Bootstrap 5.3 component or utility when one fits. Most of the app is plain Bootstrap.
  2. If a pattern repeats and Bootstrap can't express it, add a class to the right section of app.css and add it to the Class reference here.
  3. Update the example in this document in the same change, so the example and the code never disagree.
  4. No page-level <style> blocks and no style="" attributes, except for values only known at runtime (e.g. a theme swatch's colour from the database).

The theme menu at the top re-colours this page with each preset in App\Core\Theme::PRESETS (mirrored in this page's script), so you can check that a component follows the theme.

Colour

One primary family, one accent, warm neutrals, and Bootstrap's semantic colours. Colours are CSS custom properties (tokens) defined in app.css. Components use tokens or Bootstrap classes, never hex values.

Brand tokens (themeable)

Administrators choose these in Settings → Appearance (a preset from App\Core\Theme::PRESETS or custom Primary and Accent colours; admin/settings/update-appearance.php saves them). views/partials/head.php outputs theme_style_tag() after app.css, which overrides the defaults below on every page. For a custom theme, 800 and 900 are derived by darkening the chosen 700.

Bootstrap follows the theme

The Bootstrap bridge in app.css points Bootstrap's own variables at the tokens, so these Bootstrap classes are brand-coloured with no extra work. Use them freely:

A link text-primary text-bg-primary

Also bridged: border-primary, bg-primary, breadcrumbs, nav-link and close-button focus rings, list-group active items, dropdown active items and pagination. Not bridged yet (unused so far): form switches, ranges, progress bars, nav pills, accordions. Bridge them in app.css §3 before first use.

Rules

  • Use var(--color-primary-700) etc. in CSS, and text-primary, btn-primary etc. in markup.
  • Use the primary colour for what should be acted on: main actions, links, active navigation.
  • Use the accent sparingly, for small secondary emphasis (e.g. the Lecture badge in the Studio editor, the slanted block in the slide brand band below).
  • Emails and printed documents never use the theme: they are white with dark text, so any logo and any theme colour stay legible. Emails (views/emails/layout.php) are a white card with a subtle border and shadow: the logo, when one is set, and the company name on white, then the message (design.md §3).
  • Hard-code a brand hex value, or rgba(15, 93, 95, …). It breaks every other theme.
  • Use the accent or warm pink to mean error, warning or success. Those are semantic colours.
  • Pick a colour per card or per status "to make it pop".

Slide brand band

The one decorative use of the brand colours: each slide card (inductee induction page and Content Blocks Studio) has a band along its top and bottom edge, in primary 700 with a slanted accent block. The bottom band is the top one turned half round. It follows the theme, is aria-hidden, and goes on slides only.

Adding an admin page

Add one entry to views/partials/admin-menu.php, under its group. It then appears in the sidebar and as a dashboard shortcut. The key is the value the page sets as $currentPage.

  • Application: a feature of the induction domain (documented under docs/application/). Core: something any white-label deployment has (users, media, tools, settings; docs/core/). This matches the Core / Application grouping in Settings.
  • Order items within a group by how often they are used. Pages without their own entry (forms, a certificate, an exam) set $currentPage to their parent section.
  • If a group grows past about eight items, split it into a new labelled group rather than nesting menus.

Responsive

Every page must work from a 360px phone to a wide desktop, using Bootstrap's grid. No separate mobile pages.

  • Side-by-side form fields use col-sm (they stack on phones), never plain col.
  • Tables sit in .table-responsive and scroll sideways rather than squeeze.
  • The filter bar's search box is col-12 col-sm-auto.
  • In admin pages, split into side-by-side columns at xl, not lg: from lg the sidebar takes 240px, so an lg split is cramped (e.g. col-xl-8 / col-xl-4 in the Media Library).
  • Row actions stay on one line: td.text-end.text-nowrap.
  • Rows of buttons use a flex parent with flex-wrap and gap-2.
  • Fixed pixel widths on layout elements (other than the width classes above).

In a view, each field follows this recipe:

Help in a tooltip

For a form with many fields where a form-text line under each would be a wall of text (the Settings tabs): an info button after the label, its tooltip the help. Its aria-label is the same text, and the control points at it with aria-describedby, so screen readers still hear it. Tooltips start automatically (assets/js/app.js). Errors still show as invalid-feedback under the field.

After a checkbox, it follows the form-check-label. For a radio group, it goes inside the legend (with .required on a span around the legend's text), so the group's name carries the help. Help with a link or code to click or copy stays visible text.

  • A placeholder shows what a blank field will use (here, the Company Name). With no such value, leave it out; never use a placeholder as the label or as an example.

Groups, choices and input groups

Delivery
Choose how often to send.
MB
  • Mark every required field with a red asterisk: add required to its form-label (or to the legend of a required group), and give the control the required attribute, which is what screen readers announce. The asterisk itself is hidden from them. A field without an asterisk is optional; don't add "(optional)".
  • "Required" means the server rejects the form without it. A field whose blank value has a meaning ("Blank uses the Company Name", "Leave blank to keep the current password") is optional. A field required only in some cases (Primary and Accent, when Custom colours is chosen) gets the asterisk where it is shown.
  • Fields labelled only by aria-label (filter bars, one-field inline forms such as "New category name") have no visible label to carry an asterisk; their purpose makes them obviously required.
  • Group radios and checkboxes in a fieldset; its legend (form-label fs-6) must be the fieldset's first child.
  • When the error can't sit directly after the control (input groups, radio groups, custom pickers), use invalid-feedback d-block.
  • A form-level error ("Invalid email or password") is an alert alert-danger above the fields.
  • Use the right input type and autocomplete (email, tel, number, new-password…). Values the user can't change here: a disabled control. A record page with no edit form uses read-only fields.
  • Labels use the database/business term (docs/rules/terminology.md).
  • text-danger small for field errors, or placeholder text instead of a label.
  • A multi-step wizard for a long form: split it into cards or fieldsets instead.

Charts are drawn by Chart.js (pinned, from jsDelivr) in a page script that reads every colour from the tokens, so they follow the theme. Reference: the admin dashboard (views/admin/dashboard.php, assets/js/dashboard-charts.js).

Chart card

A titled card: h2.fs-6.mb-1, a text-muted small line saying what is counted, then the canvas inside .chart-box, which sets the height. The canvas is aria-hidden; the figures are always also in a table (for a single series, a table inside a div.visually-hidden: the class on the table itself doesn't shrink it, and widens the page on a phone). With nothing to plot, the card shows a text-muted small line instead.

Danger Zone

Destructive actions (Delete, Revoke) never sit in a list next to everyday buttons. Lists only navigate: their rows offer Edit or View. The destructive actions live inside the record, in a Danger Zone card at the bottom of its page, set apart from the form or details above. Each action says what it will do, and still asks for confirmation.

Danger Zone

These actions can't be undone.

Revoke this compliance record
The certificate stops being valid straight away. The record stays in the compliance history.
Delete this compliance record
Permanently removes the record and its certificate. Use only to correct a mistake.
  • Place it last on the record's page, after the form card (mt-4 inside the page's .page-narrow). Edit pages have one (Induction, Exam, User); read-only records get a detail page to hold it (Compliance Record, Exam Attempt).
  • One row per action: what it does in plain words, including what happens to related records, then an btn-outline-danger btn-sm button naming the action and the object ("Delete Induction").
  • An action that isn't available stays visible but disabled, with the reason as its description (e.g. deleting your own account).
  • Controllers: after a successful delete, redirect to the list. If the action is refused (e.g. related records exist), or after a revoke, redirect back to the record page so the message appears next to the Danger Zone. Enforce every rule on the server as well, not only in the view.
  • Delete, Revoke or trash icons in a table row, a list item or a card grid.
  • Danger Zone buttons in solid btn-danger: that is only for the final confirm button.

Lists of items without their own page

  • Selectable collections (Media Library files): select items, then use the toolbar's "Delete Selected", which confirms.
  • Small inline editors (Media Library categories): the row shows only Edit; "Delete category" appears in the edit state, and confirms.

Confirmation

Every destructive action asks first. Pick the lightest confirmation that fits:

  • Native confirm() for an action with no options: onsubmit="return confirm('Delete this exam attempt? This cannot be undone.');"
  • Modal when the user needs an explanation or a choice (e.g. cascade delete). The modal lives on the record page, with the record's id in its form.
  • Two-step page when the effect needs reviewing first (Search & Replace's dry run).

Wording: "{Verb} {object}? {Consequence}. This cannot be undone." The confirm button repeats the verb and object.

Read-only fields

A record with no edit form (Compliance Record, Exam Attempt) shows its values as readonly form fields, laid out like a form: label above, row g-3 for fields that belong together. A related record is a View button in an input group after its field. There is no <form> and no .form-actions.

View user
  • readonly, not disabled: the value can still be focused, selected and copied. app.css gives it the disabled fill so it doesn't look editable. Inside an edit form, a value that can't change there stays a disabled control.
  • No name attribute; id and label for as on any field. Use type="text" for dates, so the browser adds no picker.
  • The field shows the related record's name (user, induction, certificate number…); the View button (btn-outline-secondary) goes to its page, with the object in a visually-hidden span, so it reads "View user".
  • No value: leave the field empty with placeholder="None", and no View button.
  • Statuses are the plain label ("Active", "Passed"), as in an edit form's Status field; badges are for lists.
  • The last field or row has no mb-3, since no .form-actions follow.
  • Label/value text (<dl>) or a heading and badge in place of fields, or inline text links to related records.

Automatic. assets/js/app.js disables the button that submitted any POST form and adds a spinner, so a slow request can't be sent twice (it also restores the button if the user comes back with the browser's Back button). Nothing to add to a page. Opt a button out with data-no-loading.

Review checklist

Before merging a UI change, check:

  1. The page uses a layout partial and starts with .page-header (breadcrumb if it is below a section index).
  2. A new admin section is one entry in admin-menu.php, under Application or Core. Nothing else lists sections.
  3. Every class is Bootstrap or listed in the Class reference. No style="" or <style> for fixed values.
  4. No brand hex values; it still looks right with every theme in the menu above.
  5. Statuses use status_badge(); coloured text uses text-warning-emphasis, not text-warning.
  6. One btn-primary per form or card; Cancel is btn-outline-secondary; Delete and Revoke only in the record's Danger Zone, never in a list, and they confirm first.
  7. Fields: label, is-invalid + invalid-feedback, required fields marked (.required on the label plus the required attribute), col-sm for side-by-side.
  8. Lists: .card-table, visually hidden "Actions" heading, empty row, filter aria-labels.
  9. Icon-only controls have aria-label and title; decorative icons have aria-hidden="true".
  10. Works at phone width with no sideways page scroll (tables may scroll inside their card).
  11. Labels use the terms in docs/rules/terminology.md.
